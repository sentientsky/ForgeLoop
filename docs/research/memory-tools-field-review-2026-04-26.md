# Memory Tools Field Review

Date: 2026-04-26

This review combines the supplied transcript with a fresh web check of current Claude Code memory tools.

The question was: how should ForgeLoop V3 borrow the best ideas without copying brands, code, protected wording, or fragile complexity?

## Main Finding

The strongest systems do not try to load more memory.

They load less memory, then let the agent drill down only when needed.

ForgeLoop should therefore optimise around progressive disclosure:

1. Always-loaded rules stay small.
2. A compact pointer packet selects likely memory.
3. Exact markdown sources are opened only on demand.
4. Future semantic or graph search can sit behind the same packet contract.

## Tools Reviewed

| Tool or pattern | Useful idea | Risk to avoid | ForgeLoop decision |
| --- | --- | --- | --- |
| Claude Code native memory | Project instructions, rules, imports, auto memory, and hooks are first-class. | Stuffing too much into `CLAUDE.md` burns context every session. | Keep `CLAUDE.md` compact and use indexes or packets for deeper memory. |
| Structured `.claude/memory` patterns | Topic files and indexes reduce repeated context. | Hook-based injection can silently add too much. | Use explicit packet generation first, then optional hooks later. |
| memsearch | Markdown as source of truth, hybrid search, progressive disclosure. | Vector stores can become opaque if treated as the source. | Keep markdown canonical. Treat indexes as rebuildable. |
| claude-mem | Automatic capture, progressive search, token-cost visibility. | Worker services, databases, and automatic injection raise portability and security load. | Borrow the three-layer idea, not the heavy runtime. |
| MemPalace-style verbatim memory | Exact recall and symbolic pointers are powerful. | Opaque AI-only dialects, automatic verbatim capture, and database-first storage are harder to audit. | Use human-readable FCP packets with exact markdown references. |
| Karpathy LLM Wiki | Raw sources plus maintained wiki creates compounding knowledge. | A wiki can become busywork if it is not tied to action. | Use captures and solutions as the ForgeLoop operational wiki. |
| Recall-style hosted graph | Easy capture from articles and videos. | Hosted data ownership and pricing are not ideal for open source defaults. | Keep ForgeLoop local-first and export-friendly. |
| Open Brain | Cross-tool memory through a database and reusable skills. | Setup and remote data surface are heavier than the MVP. | Future optional connector, not core V3. |
| Mem0 | Production-ready multi-level memory. | External dependencies and cloud defaults can reduce control. | Learn from multi-level memory, keep core dependency-light. |
| LightRAG | Graph retrieval can improve complex research. | It is overkill for most project memory workflows. | Consider later for enterprise research mode only. |

## Borrowed V3 Ideas

- Markdown remains the source of truth.
- Derived indexes can be rebuilt.
- Retrieval should start with a small result set.
- Exact source content should be opened only when needed.
- Context packets should include token or byte awareness.
- Daily or session captures should be promoted into durable solution notes.
- Hooks should be dry-run and opt-in before automatic injection.
- Secrets must stay outside memory and logs.

## Rejected Ideas

- Opaque symbolic language that humans cannot inspect.
- Automatic verbatim capture of every conversation by default.
- Claims of 80 or 90 percent token reduction without measurement.
- Database-first memory in the open source core.
- Remote-hosted memory as the default.
- Active hooks that inject context before they have tests and clear limits.

## V3 Direction

ForgeLoop V3 should be a memory operating system, not a memory dump.

The new rule is:

```text
compact by default, exact by reference
```

This is implemented through FCP/1 packets generated by:

```bash
python -m forgeloop pack "task query" . --limit 5
```
